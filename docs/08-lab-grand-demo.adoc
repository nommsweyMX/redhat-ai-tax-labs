= Lab 08 — One loop, end to end

[cols="1,3"]
|===
| Product   | {rhoai}, Ansible Lightspeed, {eda}
| Rung      | data → information → knowledge → judgement
| Time      | About 8 minutes
| Script    | `labs/lab08-grand-demo/run.sh`
| Outcome   | One platform carrying logs, scores, drafts, review, automation and answers, with the loop as the knowledge base

== Objective

Mainframe and server logs come in, a predictive model scores which systems
will fall over next, Ansible Lightspeed drafts the rulebook and playbook, a
person reviews and merges them, Event-Driven Ansible runs them, and the
assistant answers "how is server8-audits?" by probing the estate. One platform
carries every step, and the loop is also the knowledge base.

On the ladder this lab climbs every rung in order. The log lines are data; the
outage-risk score is information about one system; the drafts, the review
thread and the job outcome become knowledge the moment they are merged and
indexed; and the merge itself is judgement, a determination a named reviewer
signs. Automation executes that judgement. It never makes it.

This is the lab that ties the other seven together: the tabular model from
<<lab-02>>, model serving from <<lab-03>>, retrieval from <<lab-04>>, the
rulebook and job history from <<lab-05>>, and the operations corpus from
<<lab-07>>, on the one platform <<lab-01>> and <<lab-06>> keep inside the
boundary.

== What you use

* Two model pods side by side on *OpenShift AI*: a tabular outage-risk scorer
  (sklearn on KServe) and Granite on vLLM, one namespace, one GPU node
* *Vector* and *Loki* ingesting z/OS SYSLOG, RHEL journald and OpenShift
  container logs into one queryable store
* *Ansible Lightspeed* (on-prem, its model served by OpenShift AI) drafting the
  playbook and rulebook, then a pull request for the human review
* *Event-Driven Ansible* running the promoted rulebook, and the ops assistant
  probing hosts through approved job templates

== What to notice

* The scorer produces a *number*; the drafter produces *YAML*; neither runs
  anything until a person merges the pull request
* The merge is the promotion: repo, AAP project and knowledge base update in
  one step
* Every assistant answer carries citations and a job id: evidence, not fluency
* Nothing left the cluster: mainframe logs, scores, drafts and answers all
  stayed inside the boundary

== Prerequisites

For live mode: {rhoai} with a KServe sklearn runtime for the outage-risk model
and vLLM for Granite; OpenShift Logging with Vector receiving z/OS SYSLOG
beside journald and container logs into Loki; {aap} 2.5 with Ansible
Lightspeed on-prem, its model served through OpenShift AI model serving; an
{eda} controller with the named job templates; an ITSM webhook for the ticket;
and `oc`, `logcli`, `python3`, `ansible-rulebook`, `ansible-lint`, `git`, `gh`
and `awx` on the path.

As with <<lab-07>>, the helpers the script calls (`ingest_estate.py`,
`score.py`, `lightspeed_draft.py` and `ask.py`) are representative wrappers
and are not shipped in the lab directory. What is shipped beside `run.sh` is
the Lightspeed prompt (`prompts/memory-pressure.txt`) and the reviewed,
post-merge rulebook and playbook (`rulebooks/memory_pressure.yml`,

If a score arrives without drivers, a draft arrives without citations, a job
runs that nobody merged, or an answer arrives without a job id, that is the
finding. Each of those is the same failure the earlier labs guard against,
and the loop is only as trustworthy as its weakest gate.

== Two kinds of mathematics, one platform

Two different mathematics share one platform. The outage-risk model is tabular
prediction: hourly features per system (memory headroom, GC pauses, abend
rate, batch overlap) fitted to 180 days of history, so its output is a
probability, not an explanation. The drafts come from a code model predicting
tokens, steered by your prompt and the runbooks retrieved as context, so its
output is plausible YAML that must be reviewed like any other change.
Event-Driven Ansible contains no machine learning at all: the same event
always runs the same approved job. The knowledge base grows because every
promotion (the pull request, its review thread, the job outcome) is embedded
into the same vector store the assistant searches, which is why the assistant
can cite RB-214 an hour after it was written.

IMPORTANT: One platform runs the predictive model, the generative model, the
automation and the knowledge base, so the loop that keeps systems up is also
the documentation, and the assistant answers from what the loop wrote.

== Troubleshooting

`logcli` returns only one of the three sources::
The label is `source`. Check the Vector pipeline receiving z/OS SYSLOG and the
journald forwarder on the RHEL hosts; `oc -n openshift-logging get
clusterlogforwarder` shows what is wired.

The scorer answers but every risk is 0.0x::
The feature window is too short or the model was trained on a different
estate. Re-run the ingest with the 30-day window and confirm the model version
in the registry matches `outage-risk v14`.

The draft has no citations::
Lightspeed is answering from the model alone. Point it at the <<lab-07>>
operations corpus so RB-207, CR-9120 and INC-2311 are retrievable, and treat an
uncited draft the way <<lab-04>> treats an uncited answer.

The rule matches but no job launches::
The job template name and organization must match Automation Controller
exactly, and the activation must have restarted after the merge. Same
troubleshooting as <<lab-05>>.

The playbook refuses to restart the service::
That is the `maintenance_window` guard from the review. Outside the window the
second rule opens a change request instead; a person decides.

The assistant answers without a job id::
It is answering from memory rather than probing. Every host answer should
carry a `job_template.launch` line; if it does not, the tools are not wired
and the answer is fluency, not evidence.
